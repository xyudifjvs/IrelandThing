# Live client checklist UI

The coordinator transaction page and authenticated portal transaction page now use a shared single-flight polling hook. It reads the canonical matter every 3 seconds after the prior read settles, times each request out after 4 seconds, and ignores obsolete responses. Successful reads update existing content without a loading-screen refresh. Offline, failed, timed-out or hidden-page reads clear displayed data; online, focus, visible and pageshow events reconnect immediately. A live status and retry control explain connection failures. Clearing on hidden/offline may close an in-progress edit; visible successful polling preserves task and deadline drafts and flags revision conflicts.

Coordinators can edit checklist titles, visibility, due dates, status and completion; add or delete steps; and move steps up/down. Reorder submits all canonical task IDs and the matter revision. Private steps remain under My notes & to-do, where their edit control can explicitly change visibility. Deadline drafts preserve their captured revision and require using the latest date after a concurrent change.

`ChecklistShare` is reused by the coordinator and authorized agent portal. It previews only `visibility=client` task titles, explains the link's scope, generates/replaces/revokes a link, and provides both clipboard copy and a selectable read-only field. Existing links cannot be retrieved. The complete generated URL lives only in component memory and disappears when sharing metadata indicates another generation. Both GET and POST sharing responses must supply the same `createdAt` generation timestamp; rotation must update it.

`/checklist#TOKEN` is a mobile read-only shell. Only `/api/public/checklist` receives the credential, in an Authorization Bearer header with credentials omitted, no-store reads and no-referrer. The token never appears in the request URL. The shell contains no outgoing links, contact data, documents, account or AI controls. It displays the API allowlist (matter title/address/stage, client tasks and confirmed dates). The route has noindex/nofollow/noarchive and no-referrer metadata/headers, plus no-store response configuration and request-time rendering.
