# Launch services handover

Owned scope: `packages/billing/**`, `packages/assistant/**`, `packages/assistant-ui/**`, `packages/ai/**`. No schema changes or new dependencies. No provider account calls, real messages, payments, or preview database writes were made.

## Payment contract

`STRIPE_MODE` defaults to `test` only when absent. Invalid/empty values fail closed. Live mode requires all of `STRIPE_MODE=live`, `PAYMENT_LIVE_APPROVED=true`, `DEPLOYMENT_ENV=production`, and `APP_ENV=production`. Authentication/build settings alone cannot authorize money. Staging must retain test mode and `DEPLOYMENT_ENV=staging`.

`assertPaymentKey` permits only the matching server-side `rk_`/`sk_` mode prefix. `stripeClient`, used by outbound account/checkout/refund/reconcile and signature verification, enforces the gate before networking. Ireland's actual account-ID check remains in `verifiedStripe`. Signature verification and event application both validate envelope mode, and an object's explicit `livemode` must agree. Existing signature/idempotency/amount/order logic remains intact. Account sandbox checkout/refund acceptance and Ireland's fee/gift terms remain external launch gates.

Tests can import `paymentMode(env?)`, `assertPaymentKey(key,env?)`, `assertPaymentEvent(event,env?)` from `packages/billing/src/mode.ts` without networking or database access. A signed synthetic live event is rejected locally by `verifyStripeWebhook` in test mode.

## Assistant retrieval and answer contract

`retrieveSources(actor,input,readers?)` uses the same authorized domain readers as API/MCP, paginating up to 5,000 matters, 1,000 documents and 1,000 records per selected kind. Scoped questions include current matter/tasks/deadlines/notes plus payment/gift/message records. Portfolio questions include current matters and relevant payment/message families. Document text is scanned across current versions with overlapping chunks and question tokens plus deterministic domain expansions (closing/settlement, amendment/extension, etc.), up to eight million text characters. This is lexical relevance retrieval, not semantic search or a guarantee that every relevant fact will be found.

The answer context contains at most 70 source excerpts and 90,000 content characters. When both exist, current records and document excerpts each have a 45,000-character reservation; neither can crowd out the other. Coverage is server generated and includes an as-of timestamp, scan counts, unreadable documents, selected sources/characters, omissions and history truncation. It is returned by `POST /assistant/ask`, saved on the assistant message and displayed by the assistant UI even when the model omits caveats. Source reads and answer/verification metadata are audited without source text or questions. Complete records remain reachable via existing paginated API/MCP reads; `search_evidence` now matches question tokens throughout each document page instead of the complete question as a literal substring.

`answerSchema` now returns `claims[{text,citations[{sourceId,quote}]}]` and enumerated uncertainty codes. Every claim needs real exact quotes from this request. A second independent inference pass evaluates every claim's entailment, negation, current status, amendments and contradictory retrieved evidence. Missing/duplicate/negative verdicts, invalid quotes or no claims cause a server-authored abstention. Only checked claim text and server-authored caveats are rendered; free-form answer/uncertainty prose cannot bypass the claim gate. This semantic verification is probabilistic and does not prove all statements correct. The same route/model performs both passes; real-contract/representative acceptance remains necessary.

Saved followups include actual prior user/assistant messages as untrusted context, at most 12 messages / 12,000 characters. The last two user questions also guide retrieval. Earlier assistant text is not evidence. Conversation ownership, matter-scope consistency and optimistic save checks remain enforced. A 200-message storage cap requires a new conversation. Other roles still cannot use the coordinator assistant; domain/API/MCP reads preserve their existing roles and visibility.

## AI cost/request controls and synthetic evaluation

The gateway preserves the approved OpenRouter-only ZDR/provider allowlist/no-fallback/no-plugin boundary. Optional operator ceilings: `AI_MAX_CONTEXT_CHARACTERS` defaults 180000 (hard maximum 180000), `AI_MAX_OUTPUT_TOKENS` defaults 6000 (hard max10000), `AI_MAX_PROMPT_PRICE_PER_MILLION` defaults5 (hard max100), `AI_MAX_COMPLETION_PRICE_PER_MILLION` defaults25 (hard max500). Invalid/negative/nonfinite values fail before networking; output requests must be positive integers. OpenRouter receives `provider.max_price` for prompt/completion and `request:0`, plus `usage.include=true`. Usage retains `costUsd`, null when unavailable (never silently zero). Each process allows at most four in-flight gateway requests; the parent API owner adds authenticated request throttling. These controls do not replace provider/account daily spending limits across API and worker processes.

An ask uses one generation request (max3500 output tokens) plus at most one claim verifier (max1200). No retry loop or fallback. `runSyntheticAssistantEvaluation(generate?)` from `packages/assistant/src/evaluation.ts` exports a database-free 5-case harness: factual date, amendment, conflicting amendments, injection against current payment status, and missing evidence. It uses at most10 requests with a supplied adapter; results include pass/fail, output, and usage. `syntheticAssistantCases`, `answerSchema`, and `verifyAnswer` are exported for exact route evaluation. This is synthetic acceptance, not account privacy approval or real-contract validation. The production gateway has no test bypass. The parent owns any user-authorized synthetic OpenRouter run.
