# Supplied Weatherly intake records

The November 2026 buyer, seller, buyer compliance and seller compliance forms save their original named controls in the optional `referenceIntake` object. The existing top-level intake fields remain the operational projection for legacy workflows. Existing drafts and historical submissions need no migration.

```ts
{
  version: 1,
  variant: "buyer" | "seller" | "buyer-compliance" | "seller-compliance",
  fields: Record<string, string | boolean>,
  uploads: {
    contractDocs?: string[],
    hoaFiles?: string[],
    utilFiles?: string[],
    policyFiles?: string[]
  },
  fileNames: Record<string, string>
}
```

`fields` includes the structured address (`a_num`, `a_street`, `a_city`, `a_state`, `a_zip`), seller occupancy (`occ`), clients (`b1_name`, `b1_email`, `b1_phone`, etc.), relationship (`buyerRel`, `buyerRelOther`), co-op and additional contacts (`co_*`, `c1_*`, etc.), title and lender paths/contacts, fee and commission instructions, HOA source/delivery answers, buyer MLS instructions, seller utilities/policy notes, gift choice/acknowledgment, and the separately approved contract-location field (`contractLocation`). Boolean values are reserved for `docsDotloop` and `giftAgree`. Branch changes retain hidden answers and previously uploaded evidence; a retained answer is not a new authorization.

Submission validates entered email addresses and dates, version/representation/service consistency, field lengths and upload limits. Draft saves remain available at any point, including incomplete answers. Plain **Contract to Close ($425)** requires a saved executed-contract upload in `contractDocs` (legacy upload IDs remain valid for the legacy form). **Contract to Close + Compliance ($515)** accepts that upload or an identified transaction loop: `fields.contractLocation` may name the loop, or `fields.docsDotloop` together with `fields.transactionName` or the property address identifies it. A deep URL is not required. A bare checkbox without any identifying information is insufficient. The exact dictated provider terminology remains pending; these answers create coordination work, not a new provider integration. Legacy compliance final submission accepts a selected Dotloop source and saved loop ID. Final reference submissions also require the applicable questions and original required fields, accepting the supplied unknown/help paths. Validation is active-branch-only; hidden invalid email/date answers stay saved and do not block. The complete matrix is in `FINAL_VALIDATION.md`. Each group accepts at most 30 saved IDs, at most 120 unique intake documents overall; legacy intake still accepts at most 30 contract IDs. The legacy checklist fields retain their own 30-document limit.

Every upload group is included in the server's document ownership, committed-version and unassigned-document checks. Group-only uploads are associated with the resulting matter even when absent from top-level `documentIds`. A failed assignment rolls back the draft claim, receipt and matter. HOA-only evidence never substitutes for an executed contract in follow-up tasks. Extraction failure or a request for OCR does not remove an otherwise stored original file.

Both `Matter.details.referenceIntake` and the immutable `IntakeSubmission.snapshot.referenceIntake` retain the complete data. Existing matter API authorization exposes details to the owning agent and coordinator; client projections omit details. Coordinator-only assistant `intake_drafts` and `intake_submissions` record reads retain these objects. Private documents remain accessible through their existing authorized metadata/download routes. `fileNames` is presentation metadata; canonical document names, versions, checksums and bytes remain in the document store.

Additional contact answers create review tasks; they create no users, invitations or portal grants. Dotloop answers create review/follow-up work and do not connect an account or fetch files. Gift acknowledgment and supplied policy copy create no charge, credit, refund or paid state. Ireland approved the service mapping: `essentials` is **Contract to Close, $425 USD** and `complete` is **Contract to Close + Compliance, $515 USD**. New reference submissions must match their variant to the corresponding code. Full Listing is **Coming soon** and cannot create a new submission or payment request; its saved drafts remain resumable and historical receipt/order replays remain accessible.

The additive `20261105010000_weatherly_service_catalog` migration changes only current catalog rows and increments changed catalog revisions. It does not update historical matters, submission snapshots, payment amounts/snapshots or gifts. New intakes create a `pending_review` matter with `fileReview.status: "pending"` and a durable receipt. They do not activate the transaction workflow. Ireland’s separate confirmation creates the active file; the submitted snapshot remains unchanged.

Every new submission stores an authoritative `serviceSnapshot` (`code`, `name`, `revision`, `priceCents`, `currency`, `dueAtClosing: true`, `noFeeIfTerminatedBeforeClosing: true`) in both matter details and the submission snapshot. New checkout requests use the transaction’s saved approved `serviceSnapshot` when present, rejecting a mismatch with `Matter.packageCode`. Older transactions without that snapshot use the approved current server catalog. Existing orders are returned before current catalog checks, preserving their original prices. The Full Listing catalog row retains its historical $625 value with `approved: false`; clients should display Coming soon and no order control.

Service payments are due **at closing**. Intake never creates an order or checkout. An explicit coordinator request issues checkout for the saved approved package and price; agents can resume only that issued request through their authorized account route and cannot select a different package or amount. New service orders record `dueAtClosing: true` in their immutable snapshot and details, plus coordinator/request-stage metadata. Account payment projections disclose `dueAtClosing`. New requests require a confirmed file in the existing Closing/Closed phase and Ireland’s explicit action. No calendar-date or automatic charge trigger is inferred. Retained historical orders replay from their saved records. Existing issued orders and their timing snapshots are unchanged.

A transaction that terminates before closing owes no service fee. Internal creation and resumption of an unpaid service checkout are blocked for terminated matters. Existing paid/refund history is retained without automatic refunds, charges, cancellations or reopening transitions. A durable expiration worker now handles explicitly confirmed pre-closing terminations through the gated Stripe adapter. An external URL is not represented as expired until Stripe confirms it. Actual sandbox acceptance remains an Ireland-owned account dependency; when delivery is disabled or configuration unavailable, internal denial alone does not invalidate an already distributed external URL. See `packages/billing/TERMINATION.md`.

A replacement contract creates a separate intake and pending-review matter with optional `replacesMatterId`. The referenced transaction must be authorized and terminated. Representation must match, and supplied property addresses must match after case/whitespace normalization when both records have addresses. Empty new addresses remain empty rather than copying old facts. The link lives in the new matter details and submission snapshot; the prior matter, documents, communications, payments and history remain unchanged. Previously assigned documents cannot be reused as new-contract evidence.
